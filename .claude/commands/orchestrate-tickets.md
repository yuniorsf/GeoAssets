Run multiple Jira tickets in parallel, each in its own isolated git worktree, each implemented and shipped by its own worker agent (via `/ship-ticket`), then rebase and merge all of them back into `develop` one at a time, resolving conflicts by handing them back to the worker that wrote the conflicting change. Argument: either a space/comma-separated list of ticket keys (e.g. `XD01-180 XD01-181 XD01-182`), or `JQL: <query>` (e.g. `JQL: project = XD01 AND status = "To Do" AND sprint in openSprints()`).

Default concurrency cap: 5 simultaneous workers. If resolving the argument (literal list or JQL) yields more than 5 tickets, stop and confirm with the user before spawning more than 5 workers at once — don't silently fan out wider.

**Branch base, non-negotiable:** every worktree/branch this command creates must fork from `origin/develop` — never `main`, and never "whatever branch happens to be checked out right now" (this repo's working directory is sometimes shared across concurrent sessions, so the current branch is not a reliable signal). Before step 4, `git fetch origin develop` and confirm the orchestrator's own checkout is on `develop` at `origin/develop`'s tip — don't assume it already is. `main` is never touched by this command, for any reason, at any step — not as a merge target, not as a conflict-resolution base, nothing. See `CLAUDE.md` § Branching & Release Policy.

## Steps

1. **Resolve the ticket set.** Literal keys used as-is. For `JQL: ...`, run `searchJiraIssuesUsingJql` and collect the resulting keys. Jira site: `xdicor.atlassian.net`, project `XD01` (verify with `getVisibleJiraProjects` if a call 404s).

2. **Build the merge order (not the implementation order) — and check for real parallelizability.** For every ticket in the set, `getJiraIssue` with the **full description text**, not just `issuelinks`. Dependencies in this project are not always recorded as formal Jira links — read each description for prose like "## Depends on" / "Depends on TICKET-KEY" and treat that exactly like a formal `Blocks` relation. Build the dependency graph from the union of formal `Blocks`/`is blocked by` links *and* these prose references, within the claimed set. If any ticket in the set depends (formally or in prose) on another ticket in the *same* set, that pair is not actually parallelizable — stop and tell the user rather than spawning both workers anyway, since the dependent ticket's worker would be implementing against code that doesn't exist yet in its own isolated worktree. Topologically sort what remains and break ties by Jira Rank (`ORDER BY Rank ASC`); this order is what the merge-back phase (step 5) uses — tickets with no links between them can be in any relative order.

3. **Claim tickets serially — one at a time, never in parallel.** For each ticket in the set:
   - `getJiraIssue` to check its current status.
   - If status is not "To Do": skip this ticket, note why (already In Progress / In Review / Done — someone else claimed it, or a prior run already did), and move to the next. Do not touch its status.
   - If status is "To Do": `getTransitionsForJiraIssue`, find the "In Progress" transition (don't hardcode transition IDs), `transitionJiraIssue`.
   - Only tickets successfully claimed here proceed to step 4. This ordering — check-then-transition, one ticket at a time, before any worktree or worker exists — is what makes a double-claim race impossible.

4. **Spawn one worker per claimed ticket.** For each: use the Agent tool with `isolation: "worktree"` and `name: "<TICKET-KEY>"` (e.g. `name: "XD01-180"`) — the `name` is required, not cosmetic: it's what makes this specific ticket's worker addressable later via `SendMessage` if a merge-time conflict needs resolving by the same agent that wrote the change. Prompt: "Run `/ship-ticket <TICKET-KEY>`." (If `.claude/agents/ticket-worker.md` exists, spawn that persona instead of a bare prompt, passing the ticket key as its input.) Issue all spawns for this round together, then wait for all workers to go idle before continuing.

5. **Collect results.** For each worker: worktree path, branch name, PR number/URL, final Jira status, pass/fail. Any ticket whose worker did not reach "pushed branch + open PR + In Review" is excluded from the merge-back phase below and reported to the user as needing attention — never force it forward.

6. **Merge-back phase — strictly serialized in the step-2 order.** `develop` is the only merge target, always — never `main`. For each eligible ticket, in order:
   a. In that ticket's worktree: `git fetch origin develop`, then `git rebase origin/develop`.
   b. **If the rebase is clean:**
      - Re-run `dotnet build` on the full solution and `dotnet test` on the full solution **in that worktree, after the rebase** — do not trust the pre-rebase green run; a rebase can silently reintroduce a break (e.g. an enum/interface whose meaning shifted) with no textual conflict.
      - **Hard stop, no exceptions, on any failure.** If build or test comes back red — including a failure that looks pre-existing, flaky, or unrelated to this ticket's diff — do not push, do not merge. There is no judgment call here, not from the orchestrator and not from the worker: exclude this ticket from merge, report the exact failure in the final report, and move on to the next ticket in order. A human must confirm it's safe before this ticket is retried.
      - If green: `git push --force-with-lease` (rebase rewrites history, so a force-push is required; use `--force-with-lease`, never a bare `--force`).
      - Wait for CI: `gh pr checks <number> --watch` (covers this repo's `dotnet.yml`/`unit-tests.yml` workflows, which already trigger on push/PR).
      - If CI is green: `gh pr merge <number> --rebase --delete-branch`. (There is no MCP tool for this step — GitKraken MCP has no merge action — so this one step uses the `gh` CLI directly.) If branch protection/required review blocks the merge, that's expected, correct behavior — report it, don't try to route around it.
      - Clean up: `git worktree remove <path>` and delete the local branch (`git branch -d <branch>`; the remote branch is already gone via `--delete-branch` above). Use plain `git`/`gh` here, not `mcp__GitKraken__git_worktree`/`git_branch` (those only support `list`/`add`, not removal).
   b. **If the rebase conflicts:**
      - Do not resolve it yourself. `SendMessage` to the worker **by its ticket-key name** (e.g. `to: "XD01-180"`) — this resumes it from its own transcript, inside its own still-live worktree, with full context of what it implemented and why. Include: the conflict details (`git status`, the conflicting hunks/files), and ask it to resolve consistent with its own original change, re-run `dotnet build`/`dotnet test` on the full solution itself, then `git push --force-with-lease` itself — and make explicit in that message that the same hard-stop rule applies: any test failure, even one it believes is unrelated, means stop and report back rather than push.
      - If the worker reports the conflict is not a mechanical merge — both sides changed the same behavior differently, not just nearby unrelated lines — it should `git rebase --abort` and escalate rather than guess. Treat that the same as "needs manual resolution" in the final report: exclude from merge, keep both PRs open, move on to the next ticket in order (don't block the whole batch on one ambiguous conflict).
      - Otherwise, once the worker reports success, proceed exactly as the clean-rebase path (re-test gate already done by the worker, CI wait, `gh pr merge`, cleanup).

7. **Final report.** A table: ticket → outcome (merged / needs-manual-resolution / implementation-failed / skipped-already-claimed), with PR links for anything still open. Nothing is ever force-merged or force-transitioned to Done past a failure or an unresolved conflict — surface it, don't paper over it.
