# Entity Framework Core: configuration, migrations, and the aggregate/entity tension

**Status: `current`** — EF Core mechanics (fluent config, migrations, global
filters, JSON columns) are current through EF Core 9/10.

**Source**: Gabriel Baptista & Francesco Abbruzzese, *Software Architecture with
C# 14 and .NET 10*, 5th Edition (Packt Publishing, 2026), Chapter 13
"Interacting with Data in C# – Entity Framework Core." Distilled and
paraphrased.

## Three ways to configure a mapping, and when each earns its place

Data annotations (attributes on properties), naming conventions (e.g. an
`Id` property implicitly becomes the primary key), and the fluent
configuration API can all express the same settings, with different
trade-offs. Naming conventions have **no compile-time check** — a rename
during refactoring can silently break a mapping with no error until runtime.
A reasonable default policy: rely on naming convention only for the
`Id`-as-primary-key case (a de facto standard, low misspelling risk); use
data annotations for simple *value-constraining* rules on a property
(`MaxLength`, `Required`) since placing the constraint next to the property
it restricts helps readability; put everything else — relationships,
indexes, anything modular/cross-cutting — in the fluent API (either inline in
`OnModelCreating`, or better, in a separate `IEntityTypeConfiguration<T>`
class per entity, auto-discovered via `ApplyConfigurationsFromAssembly`) so
entity classes stay uncluttered by wiring that's a different concern from
"what shape is this data."

## The DbContext is a deferred, in-memory view

`DbContext` collections are `IQueryable` — building a LINQ query against them
doesn't touch the database. The actual SQL is generated and executed only
when the query is **materialized**: `ToListAsync`/`ToArrayAsync` for
collections, `FirstOrDefaultAsync`/`LastOrDefaultAsync` for a single/optional
result, `CountAsync` for a count. Nothing before that point is a real query.

**Updates require the entity to already be loaded** into that in-memory view
first — you can't update or delete a row EF hasn't materialized. Additions
are just adding an instance to the mapped collection. None of this reaches
the database until `SaveChangesAsync()` — which is also where DB errors
surface (wrap it in try/catch) and which is the concrete mechanism behind
the Unit-of-Work pattern: everything pending across a `DbContext` instance
commits together, in one transaction, at that single call.

## Loading related data

- `Include`/`ThenInclude` eagerly load navigation collections not loaded by
  default (and, since EF 5, `Include(...).Where(...)` filters *which* related
  rows get pulled in, not just whether to load them).
- `AsSplitQuery()` breaks an overly complex single generated SQL statement
  into several simpler ones, when EF's default "one LINQ query → one SQL
  query" behavior produces something slow.
- `ToQueryString()` on a query shows the actual generated SQL — the direct
  tool for diagnosing an unexpectedly slow LINQ query.

## Migrations: a repeatable design/update loop

1. Change `DbContext`/entity definitions.
2. Generate a migration — a file capturing the diff as an `Up` (apply) and
   `Down` (undo) pair.
3. Apply the migration to update the physical database.
4. Test; loop back to 1 if more changes are needed.

A migration can be safely removed **before** it's applied; once applied,
correcting a mistake means writing and applying a *new* migration, not
editing history. Design tooling needs its own way to obtain `DbContextOptions`
(an `IDesignTimeDbContextFactory<T>` implementation), separate from how the
running app gets its options — design-time tooling runs outside the app's own
startup path.

Not everything a schema needs can be generated by diffing the model — stored
procedures, for instance, get added by hand-writing raw SQL inside an
otherwise-empty migration. The concrete case for reaching for a stored
procedure over plain EF operations: an **atomic increment/decrement**
(reserving inventory, decrementing available seats) that EF's
load-then-save round trip can't express as a single atomic database-side
operation without wrapping it in an explicit transaction — which may itself
cost more than the stored procedure would.

**Compiled models** (`Optimize-DbContext`) are a real but narrow-use
optimization — worth roughly 10x on very large models (hundreds of entities),
and worth adding *only after* confirming an actual slowdown, not by default.
They need to be regenerated after every migration, since they're tied to the
current mapping configuration.

## Projections beat loading entities for read-only queries

For read-only results consumed by an outer layer, project directly into a
DTO via LINQ `Select` rather than loading full entities and copying fields
manually — the database only needs to return the columns actually selected,
and it also respects Onion architecture's layer isolation (outer layers
shouldn't necessarily see raw domain entities).

## The core Onion-architecture tension: EF entities want to be anemic, aggregates don't

EF Core entities need publicly read/write properties for its own
materialization and change-tracking to work — which is exactly the
record-like shape DDD aggregates (Chapter 7 reference) are supposed to
*avoid*. Two ways to resolve it, neither free:

- **State-interface approach** (the book's stated preference): define a
  plain data-contract interface in the domain layer; the EF entity (living in
  the DB-driver/outer layer) implements it; the real aggregate class — also
  in the domain layer, with **no reference to the ORM at all** — wraps an
  injected instance of that interface, and every business method mutates
  state only through it. Persistence stays transparent because mutating the
  interface is really mutating the underlying EF entity. This keeps the
  domain layer's assembly completely free of any ORM dependency, honoring
  Onion's inward-only dependency rule, at the cost of more code (an interface
  + a wrapper class per aggregate) than just using the entity directly.
- **Direct mapping to private fields**: let EF map columns straight to
  private backing fields (via its underscore-prefixed-field naming
  convention) and expose only curated public members for business logic.
  Simpler to write, but loses data-annotation attributes entirely (private
  fields aren't good attribute targets for this), forces *all* configuration
  into the fluent API, and — the real cost — couples the aggregate class
  itself to DB-driver concerns, since the aggregate now lives partly defined
  by mapping needs rather than purely by domain needs. Reasonable only for
  very simple tables with little business logic; not a general-purpose choice.

## Escaping the ORM when needed

- `Database.ExecuteSqlRawAsync(sql, params)` — raw SQL that doesn't return
  entities.
- `context.<MappedCollection>.FromSqlRaw(sql, params)` — raw SQL that returns
  instances of an already-mapped entity type.
- `Database.SqlQueryRaw<TResult>(sql, params)` (since .NET 7) — raw SQL
  returning an arbitrary shape not backed by a `DbSet`; column names must
  match `TResult`'s property names, or be reconciled via `[Column("...")]`/
  `HasColumnName(...)`.

Practice: keep raw SQL strings in resource files, and wrap these calls inside
methods on your `DbContext` subclass — that keeps the DB-specific dependency
encapsulated in the driver layer instead of leaking into every caller.

**Explicit transactions** (`Database.BeginTransaction()` + try/commit/catch/
rollback) are needed whenever a query and a later update must be atomic
together (check-then-reserve style operations) — any `SaveChangesAsync` call
made inside that block joins the already-open transaction instead of
starting a new one.

## Deployment

`context.Database.Migrate()` applies whatever migrations haven't been
applied yet, and is safe to call repeatedly/idempotently — a reasonable thing
to run at app startup when the deploying identity has schema-modifying
rights. When it doesn't (a common production constraint), `Script-Migration`
converts pending migrations into a plain SQL script for a DBA to review and
apply by hand instead. For seed data, check emptiness first (`.Any()`)
before inserting, to avoid re-seeding on every app start.

## NoSQL (Cosmos DB) differences worth knowing

Same API shape, different structural rules: no migrations (schema-less;
`Database.EnsureCreated()` instead), every `DbSet<T>` maps to its own
container by default unless explicitly grouped via `.ToContainer(...)`,
primary keys must be strings (not auto-incrementing integers — avoids
write-contention in a distributed store), and related sub-objects can be
denormalized straight into the parent document via `.OwnsOne()`/`.OwnsMany()`
instead of living in a separate table.

## Advanced features worth knowing exist

- **Global query filters** (`HasQueryFilter`) — a `WHERE` clause applied
  automatically to *every* query against an entity, without repeating it at
  every call site. The two standard uses: soft-delete (filter out
  `IsDeleted` rows globally) and **row-level multi-tenant isolation** — a
  filter referencing a property on the `DbContext` instance itself (e.g.
  `CurrentUserId`), so every query issued through that context instance is
  automatically scoped to the current user/tenant's own rows, with no risk
  of a call site forgetting to add the `Where` clause itself.
- **View + table dual mapping** (`ToTable(...)` and `ToView(...)` on the same
  entity) — read through a view, write through a real table; useful for
  gradually migrating between an old and new table shape.
- **`ConfigureConventions`** sets solution-wide defaults (decimal precision,
  default string max length) instead of repeating the same attribute or
  fluent call on every property.
- **JSON column mapping** (`OwnsOne(...).ToJson()`, nested `OwnsMany`) stores
  a complex sub-object as a native JSON column, still queryable through
  normal LINQ navigation syntax — no separate table needed for data that's
  naturally owned/nested.

## Where this would apply in GeoAssets

- `workflow/GeoAssets.Workflow.EFCore` already follows the recommended
  fluent-configuration pattern via separate `*Configuration.cs` classes
  (`ServiceOrderRecordConfiguration`, `OrderActionPermissionRecordConfiguration`,
  etc.) rather than one large `OnModelCreating` — matches this chapter's
  stated preference exactly.
- **Global query filters are a directly applicable technique for
  `Authorization.md`'s org-scoped resource design (§4)**: instead of (or
  alongside) the proposed `AuthorizationHandler<OrgResourceRequirement,
  IOrgOwnedResource>` checked per request, a `HasQueryFilter` on `GeoFeature`/
  `AssetType`/`ServiceOrder` keyed off a `CurrentOrganizationId`-style
  property set on the `DbContext` instance would enforce the
  same-org-or-granted-access rule at the query level itself — every LINQ
  query issued through that context automatically excludes rows the caller
  shouldn't see, as defense-in-depth underneath the per-request
  authorization check rather than instead of it. Worth evaluating alongside
  XD01-20/XD01-21 when that work starts.
- `providers/GeoAssets.Provider.PostgreSQL`'s `GeoEntityRow` ↔ `GeoFeature`/
  `GeoGeometry` bridge (`feature.Geometry?.NtsGeometry` written to
  `GeoEntityRow.Geom`, `GeoGeometry.FromNts(row.Geom)` read back) is the
  "map EF entities to separate classes" pattern this chapter names as the
  *first*, weaker option for reconciling anemic EF entities with a richer
  domain model — the chapter's caution there is that changes made on the
  domain-side object must reliably flow back into the EF-mapped row before
  save. Worth a quick check that `PostgresAssetRepository`'s update path
  actually re-syncs `GeoEntityRow` from a mutated `GeoFeature` correctly,
  since that's exactly the gap this pattern is prone to if the two objects
  drift independently.
